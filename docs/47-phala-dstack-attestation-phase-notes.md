# Phase: Phala/dstack Attestation Artifact Validation — Implementation Notes

New explicit implementation phase. Ships `crates/hsai-attestation-phala`, a
managed-verifier Phala/dstack artifact validator that replaces synthetic fixture
acceptance with a real captured public Trust Center artifact.

## Captured Artifact

Fixture:

- `crates/hsai-attestation-phala/tests/fixtures/phala_trust_center_app_2026_06_16.json`

Source:

- `https://trust-data.phala.com/73444697-af6e-4efe-b958-c130bce549a2.json`
- Trust Center app id `099098730db24cb5c3d6d7e24bf97c769f1be1c4`
- Captured completion timestamp `2026-06-16T14:20:17.056Z`

The fixture is non-secret and stores a reduced copy of the captured artifact:
raw TDX quote hex, `report_data`, RTMR0-3 values, ordered RTMR3 event log,
app compose JSON, Docker image digests extracted from the compose payload,
anchor id, app certificate public key, nonce/case-hash slices, and the managed
verifier metadata.

## Verification Mode

This phase uses managed Phala Trust Center/dstack verifier mode. It does not run
local Intel DCAP quote verification and does not validate Intel Trust Authority
JWT signatures locally. The validator therefore records the managed dependencies
as explicit trust roots:

- `managed:phala-trust-center`
- `managed:intel-trust-authority`
- `dstack-os:<os_image_hash>`
- `compose:<compose_hash>`

The emitted envelope also includes the underlying hardware anchor trust root from
`hsai-distinct-agent`.

## Public API

`PhalaArtifactBundle` parses the captured evidence shape.

`PhalaValidationPolicy::for_bundle` derives a deterministic local policy from a
captured artifact. Callers can override expected report data, anchor id,
freshness window, and required Docker image digests.

`validate_phala_artifact` validates:

- anchor id matches the expected hardware anchor;
- raw quote hex and quote-extracted `report_data` are well-formed;
- `report_data` equals the expected captured challenge;
- app compose JSON hashes to the attested compose hash;
- the RTMR3 `compose-hash`, `app-id`, `instance-id`, and `os-image-hash` event
  payloads match the captured fields;
- the ordered RTMR3 event-log digest chain replays to the quoted RTMR3;
- the observed timestamp is fresh under the policy window;
- required Docker image digests are present in the extracted compose digests;
- managed verifier metadata is present and accepted.

`PhalaAttestationLane` emits the same
`Anchor::validity_assumption(subject)` guarantee as `hsai-attestation`, with
`Maturity::Attested`. It never emits `Proven`.

## Claim Boundary

This is real captured artifact validation in managed verifier mode, not formal
proof and not local DCAP verification. A successful validation establishes only
hardware-bounded anchor validity for the captured artifact under the explicit
Trust Center and Intel Trust Authority trust roots. It does not prove application
semantics, benchmark correctness, or official benchmark evidence.

The public fixture was not generated by this repository with a fresh HSAI
challenge protocol. Its `report_data` is checked exactly, and the fixture exposes
nonce/case-hash slices for deterministic local tests. A future stronger capture
should bind `report_data` to an HSAI-owned `agent_pubkey || nonce || case_hash`
challenge before Phase 4 claims broader operational readiness.
