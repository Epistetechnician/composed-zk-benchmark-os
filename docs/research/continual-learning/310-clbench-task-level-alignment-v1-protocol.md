## Benchmark selection

The primary benchmark is the Apache-2.0
[Continual Learning Bench](https://github.com/pgasawa/continual-learning-bench),
paired with its paper
[Continual Learning Bench: Evaluating Frontier AI Systems in Real-World
Stateful Environments](https://arxiv.org/abs/2606.05661). Its task unit is an
ordered sequence of task instances with feedback and reward. The six declared
task IDs are:

`blind_spectrum_monitoring`, `codebase_adaptation`, `cohort_studies`,
`database_exploration`, `exploitable_poker`, and `sales_prediction`.

The benchmark binding is frozen before review to release commit
`9cc63c0f429048b843e8d43ac4f2b0ea4df13724`, tree
`ec757e2d999d895a7beec03270c6d014c01f2915`, and the task-manifest paths
`src/tasks`, `configs`, `src/registry.py`, `src/system_manifest.py`,
`pyproject.toml`, and `uv.lock` in that external checkout. Any change to the
release, task roster, schedules, dependency lock, protocol, validator, or
review bundle creates a new protocol identity and requires a new review. No
benchmark bytes are copied into this repository.

Tencent’s `CL-bench Life` is not a substitute in this slice. Its dataset card
defines a custom evaluation-only license that forbids training, fine-tuning,
calibration, adaptation, and parameter updates. It therefore cannot support
the requested SGD, replay, EWC, or orthogonal update arms. A later Life study
would be a separate inference-only protocol, with a separate review and claim
ceiling.

## Scientific question

Under the same task instances, feedback opportunity, compute ceiling, memory
ceiling, and monitoring budget, does any continual-learning mechanism improve
incoming task performance while preserving performance on protected tasks?

The scientific object is task-level adaptation with retention. Recall-only,
prompt-length, aggregate reward, or a memory-size gain cannot substitute for
the paired incoming-learning and protected-retention estimands.

## Arms

Every arm is evaluated on the same paired task-instance roster. The base model
is immutable and excluded from adaptive-state accounting.

| Arm | State channel | Fixed role |
| --- | --- | --- |
| `no_update` | None | Fresh state per instance; absolute non-learning control |
| `sgd` | Parameter update | One shared online adapter with fixed SGD updates |
| `replay` | Parameter update | SGD adapter plus fixed-size replay, with bytes and replay compute counted |
| `ewc` | Parameter update | SGD adapter plus fixed Fisher penalty, with Fisher state counted |
| `orthogonal` | Parameter update | SGD adapter plus fixed update projection, with projection compute counted |
| `icl` | In-context | Full declared history context, with context bytes/tokens counted |
| `external_memory` | External memory | Fixed retrieval memory with declared write/read/delete policy |

No arm may change the evaluator, task environment, score function, split
assignment, monitor, budget, or validator.

## Task-level design

The six benchmark tasks are wrapped by a task-orchestration layer that keeps
the benchmark-native environment and reward unchanged. A family is
`task_id:order_seed:replicate_seed:family_index`.

Each incoming task block is followed by a fresh, disjoint protected-task probe
over previously exposed task families. The probe produces no feedback and
cannot write to any arm’s state. The same environment seed and instance IDs
are paired across arms, but each arm receives only feedback generated by its
own actions. This preserves the causal comparison without pretending that
interactive actions are identical.

The declared split has 90 families each for `fit`, `tune`, and `assessment`.
Fit, tune, and assessment families must be disjoint by task instance ID,
source/environment ID, feedback, and label. The assessment roster is unseen
when the prediction lock is sealed. Five repeats and three predeclared order
seeds are used; the fresh replication lane must use a new runner identity,
new custody root, and new seed set.

## Estimands and gates

For each task family, the primary incoming-learning quantity is the
benchmark-normalized reward of an arm minus `no_update` on paired incoming
instances. Protected retention is the post-incoming protected-probe reward of
the arm minus the corresponding `no_update` protected-probe reward. The
official CL-Bench stateful-minus-stateless gain is retained as a secondary
diagnostic, not substituted for the protected-task endpoint.

The fixed assessment gates are:

- at least four of six tasks have a positive lower 95% family-bootstrap
  interval for incoming learning after Holm correction;
- no task has incoming learning below `-0.02` normalized reward;
- no task has protected retention below `-0.05`, and the protected macro delta
  is at least `-0.02`;
- all seven arms satisfy the declared resource and missingness contracts;
- the fresh replication lane reproduces direction and every hard gate.

The unit of analysis is family first, then task macro-average. Ten thousand
bootstrap replicates, 95% confidence intervals, Holm correction across the
six primary task tests, and fail-closed missingness are fixed before review.
There is no imputation and no selected-cell exclusion.

## Matched resource contract

Every arm has the same hard ceilings per task instance:

- 40 environment steps;
- 8,192 input tokens and 2,048 output tokens;
- 262,144 bytes of persistent adaptive state, including optimizer, Fisher,
  replay, context, and external-memory state;
- 100,000 declared compute units, measured by the same forward/backward meter;
- one frozen-monitor call of at most 512 tokens.

The exact task roster, feedback opportunity, compute ceiling, persistent-state
ceiling, and monitor call/token ceiling are all recorded. Actual use is also
reported by channel. Base-model bytes are immutable and excluded from the
adaptive-state comparison.

## Prediction lock and custody

Fit and tune may select the arm, fixed hyperparameters, fixed monitor and
thresholds, and the assessment family/order roster. A prediction lock is
sealed before any assessment label, effect, outcome, or trace is available.
It contains one digest per assessment family and is independently recomputed.
If the lock is missing, stale, candidate-dependent after the fact, or contains
assessment information, the protocol stops.

Raw task traces, prompts, feedback, actions, and per-instance outcomes may
exist only in a new external owner-only `0700` ephemeral custody root for at
most 72 hours. The operator and validator use distinct roots. The repository
retains aggregate-only artifacts and digests after a deletion receipt. Prior
CAL, AHCL, MiniMind, Oak, Astral, Qwen, or CL-Bench result roots are not inputs.

2. Obtain a genuinely independent, packet-bound signed `ACCEPT`; the operator

3. Freeze the exact external benchmark release, task manifest, model/runtime,

4. Obtain a separate explicit execution authorization. Review acceptance alone
   does not authorize model execution, provider calls, spend, or assessment.
5. Run only qualification and fit/tune under the declared gates.
6. Seal the prediction lock and obtain the required pre-assessment review.
7. Run assessment once, delete raw traces, independently recompute aggregates,
   then run the fresh replication lane.
8. Classify `Candidate` or `NoCandidate`; retain the narrow claim ceiling.

Until steps 2 and 4 are satisfied, all execution gates remain false. This
checkout currently has neither acceptance nor execution authorization.
