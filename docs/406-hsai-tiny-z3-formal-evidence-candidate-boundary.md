# Phase 406 HSAI Tiny Z3 Formal Evidence Candidate Boundary

State slice: `Phase 406 HSAI tiny Z3 formal-evidence candidate boundary`.

## Boundary

Phase 406 defines the docs-first boundary between the Phase 405 quarantined
fixed local Z3 execution output bundle and any future local formal-evidence
candidate for:

```text
gateway-local-digest-binding-determinism-v1
```

This phase does not implement candidate metadata, reviewed evidence, accepted
evidence, Level2+ evidence, score axes, proof artifacts, checker transcripts,
solver certificates, Lean execution, COBALT execution, Rust-to-Lean extraction,
benchmark submission, or production deployment.

This phase exists to preserve the category boundary:

```text
quarantined fixed-Z3 output bundle != formal evidence candidate
formal evidence candidate != accepted evidence
```

## State Ladder

The tiny digest-binding lane now has this local ladder:

| State | Meaning | Current status |
| --- | --- | --- |
| `backend_probe_metadata` | No-spawn backend availability and digest metadata for the tiny property. | Implemented by Phase 403. |
| `quarantined_z3_execution` | One fixed local Z3 process run through the existing fixed-process lane. | Implemented by Phase 404. |
| `quarantined_z3_output_bundle` | Materialized/read-back execution output with digest sidecars and nonpromotion checks. | Implemented by Phase 405. |
| `formal_evidence_candidate` | A future local metadata record that binds the Phase 405 bundle to property, command, solver, verifier, reviewer, and nonclaim inputs. | Future phase. |
| `reviewed_formal_evidence` | A future reviewed local record over the candidate. | Future phase. |
| `accepted_formal_evidence` | A future accepted append through `zkbench-core` policy, if policy ever permits it. | Not authorized. |

No state transition may skip a state. Phase 406 authorizes no state transition
by itself.

## Required Future Candidate Inputs

A future `formal_evidence_candidate` for the tiny Z3 lane must bind all of
these inputs:

- Phase 403 backend probe digest.
- Phase 403 probe input digest.
- Phase 404 execution digest.
- Phase 404 execution input digest.
- Phase 405 output manifest digest.
- Phase 405 output manifest declared file digests.
- Fixed executable digest.
- Fixed argv template digest.
- SMT-LIB2 obligation digest.
- Expected solver verdict label.
- Solver verdict label returned by Phase 404.
- Command descriptor digest.
- Output bundle nonclaim digest.
- Source correspondence statement for the tiny property.
- Replay descriptor for reproducing the fixed local command.
- Verifier policy id.
- Reviewer policy id.
- Explicit acknowledgement that accepted evidence, Level2+ evidence, and score
  axes remain disabled.

The candidate must fail closed if any digest is missing, zero, stale, or
inconsistent with the read-back Phase 405 bundle.

## Required Rejection Cases

A future implementation must reject candidate construction if any of these are
true:

- the Phase 405 bundle fails readback;
- the Phase 404 execution record is not `SolverUnsatWithoutCertificate`;
- the Phase 404 execution did not spawn a process or did not execute the local
  backend;
- the Phase 403 probe does not select the Z3 SMT lane as available;
- any proof-artifact, checker-transcript, solver-certificate, accepted-evidence,
  Level2+ evidence, score-axis, production-readiness, SOTA, breakthrough,
  full-security, semantic-correctness, or authority flag is true;
- the candidate lacks a source correspondence statement;
- the candidate claims a whole-system proof;
- the candidate claims semantic correctness;
- the candidate claims production readiness;
- the candidate claims full security;
- the candidate claims SOTA or benchmark superiority;
- the candidate points at accepted-evidence output paths before review;
- the candidate relies on raw solver logs, raw provider responses, secrets, or
  undeclared files;
- the candidate tries to promote a checker transcript or solver certificate
  that was not generated by an implemented checker lane.

## Evidence Meaning

If a future candidate implementation passes all Phase 406 checks, the maximum
supported claim is:

```text
HSAI has a local formal-evidence candidate for one tiny gateway digest-binding
property, bound to a quarantined fixed local Z3 execution output bundle,
declared digests, replay metadata, verifier/reviewer policy ids, and explicit
nonclaims.
```

That still is not:

- accepted formal evidence;
- Level2+ evidence;
- score-axis evidence;
- a Lean proof;
- a COBALT containment proof;
- a Rust-to-Lean proof;
- a checker transcript;
- a solver certificate;
- source correspondence proof;
- whole-system security proof;
- semantic correctness;
- production readiness;
- SOTA;
- breakthrough status;
- full security;
- authority to execute an action.

## Future Code Phase Exit Criteria

Phase 407 may implement candidate metadata only if it adds:

- a tiny-Z3 candidate data model under `crates/hsai-agent-admission`;
- deterministic candidate digesting;
- candidate validation from a read-back Phase 405 manifest;
- bindings to Phase 403, Phase 404, and Phase 405 digests;
- fail-closed rejection for every Phase 406 rejection case;
- tests for valid candidate construction;
- tests for stale probe, stale execution, stale output manifest, nonclaim drift,
  solver-verdict drift, raw-artifact reliance, and promotion flags;
- docs proving the candidate remains below accepted evidence;
- no accepted Evidence Ledger mutation;
- no Level2+ evidence;
- no score-axis population.

The future code phase must not reuse the older Phase 329 data model without
explicitly adapting the inputs. Phase 329 binds Phase 323/325/327 command-lane
artifacts, while this tiny lane must bind Phase 403/404/405 artifacts.
