# Phase 328 HSAI Formal Evidence Promotion Boundary

State slice: `Phase 328 HSAI formal-evidence promotion boundary for quarantined fixed-SMT output`.

## Boundary

Phase 328 defines the docs-first promotion boundary between a quarantined
Phase 327 fixed-SMT execution output bundle and any future formal-evidence
candidate. It does not implement candidate emission, accepted evidence mutation,
Level2+ evidence, score-axis population, proof artifact generation, checker
transcript generation, solver certificate generation, Lean execution, COBALT
execution, Rust-to-Lean extraction, benchmark submission, or production
deployment.

This phase exists to prevent a category error:

```text
quarantined backend output != accepted formal evidence
```

The Phase 327 bundle may become an input to a future candidate-evidence phase
only after this boundary is implemented in code and validated. Until then, it
remains local quarantined execution output.

## Promotion States

The formal lane has four distinct states:

| State | Meaning | Current status |
| --- | --- | --- |
| `quarantined_output` | A local backend process executed and the redacted output bundle read back. | Implemented by Phase 326/327. |
| `formal_evidence_candidate` | A local candidate record binds a quarantined output to a property, source bundle, preflight, verifier policy, and nonclaims. | Future phase. |
| `reviewed_formal_evidence` | A reviewer or deterministic review policy accepts the candidate as scoped local evidence. | Future phase. |
| `accepted_formal_evidence` | The evidence is appended through the repository accepted-evidence path with explicit claim boundary and no Level2+ escalation. | Future phase. |

No state transition may skip a state.

## Candidate Evidence Inputs

A future `formal_evidence_candidate` must bind all of these inputs:

- Phase 323 real command-lane manifest digest.
- Phase 325 execution preflight digest.
- Phase 326 process-output digest.
- Phase 327 output-bundle manifest digest.
- Fixed executable digest.
- Fixed argv template digest.
- SMT-LIB2 obligation digest.
- Expected-output grammar digest.
- Solver verdict label.
- Stdout and stderr summary digests.
- Nonclaim set digest.
- Source correspondence statement.
- Replay command descriptor.
- Verifier policy id.
- Reviewer policy id.

The candidate must fail closed if any digest is missing, zero, stale, or
inconsistent with the read-back bundle.

## Required Rejection Cases

A future implementation must reject candidate promotion if any of these are
true:

- the Phase 327 bundle fails readback;
- the solver verdict is `SolverSatWitnessWithoutCertificate`,
  `SolverUnknown`, `ProcessTimedOut`, `ProcessFailed`, or
  `OutputUnparseable`;
- the output has proof, checker-transcript, solver-certificate, accepted
  evidence, Level2+ evidence, score-axis, production-readiness, SOTA,
  breakthrough, full-security, semantic-correctness, or authority flags set;
- the candidate lacks a source correspondence statement;
- the candidate claims whole-system proof;
- the candidate claims semantic correctness;
- the candidate claims production readiness;
- the candidate claims full security;
- the candidate claims SOTA;
- the candidate points at accepted-evidence output paths before review;
- the candidate reuses a stale preflight with a different Phase 323 manifest;
- the candidate relies on raw solver logs, raw provider responses, secrets, or
  undeclared files;
- the candidate tries to populate benchmark score axes;
- the candidate tries to promote a checker transcript or solver certificate
  that was not generated by an implemented checker lane.

## Evidence Meaning

If a future candidate phase is implemented and all Phase 328 checks pass, the
maximum supported claim is:

```text
This local formal-evidence candidate binds one quarantined fixed-SMT execution
output to one declared gateway admission invariant, one source bundle, one
preflight, one fixed executable digest, one solver verdict, and explicit
nonclaims.
```

That still is not:

- accepted evidence;
- Level2+ evidence;
- score-axis evidence;
- a Lean proof;
- a COBALT containment proof;
- a Rust-to-Lean proof;
- a source correspondence proof;
- a whole-system security proof;
- semantic correctness;
- production readiness;
- SOTA;
- breakthrough status;
- full security;
- authority to execute an action.

## SOTA-Quality Direction

The direction toward SOTA-quality evidence is not a stronger label on the
current artifact. It is a stricter evidence pipeline:

1. Candidate evidence must bind every source and execution digest.
2. Candidate evidence must preserve nonclaims in the data model.
3. Candidate evidence must be replayable from declared files only.
4. Candidate evidence must reject stale preflights and source drift.
5. Candidate evidence must separate solver verdicts from proof authority.
6. Candidate evidence must support later checker lanes without retroactively
   treating this output as a checker certificate.
7. Accepted evidence must be created only through the repository accepted
   evidence append path.
8. Benchmark or SOTA claims require separate benchmark evidence and external
   comparison methodology.

The defensible claim after implementing this boundary in code would be:

```text
HSAI has a scoped formal-evidence candidate lane for one gateway admission
invariant, with digest-bound replay, nonclaim preservation, and explicit
promotion rejection.
```

That is movement toward SOTA-quality engineering evidence. It is not a SOTA
claim.

## Future Code Phase Exit Criteria

Phase 329 implements candidate evidence only if it adds:

- a candidate evidence data model under `crates/hsai-agent-admission`;
- deterministic candidate digesting;
- candidate validation from a read-back Phase 327 manifest;
- fail-closed rejection for every Phase 328 rejection case;
- tests for valid candidate construction;
- tests for source drift, stale preflight, nonclaim drift, and promotion flags;
- docs proving the candidate remains below accepted evidence;
- no accepted Evidence Ledger mutation;
- no Level2+ evidence;
- no score-axis population.

The first future candidate property remains:

```text
attestation_challenge_binding_deterministic_input_sensitive
```

No broader property is authorized by this boundary.
